# 主进程目录结构与依赖规则（`src/main`）

本文是 `src/main/` 目录分类与依赖方向的权威参考：每个目录是什么、靠什么规则阻止它蔓延、新能力往哪放。

顶层是一组**封闭的、按性质划分的语义分类**，不是开放的模块清单。我们只做三处必要微调（§6）。

> 本文描述**目标态**。当前 `src/main/` 下的内核目录全是空壳：只有 `README.md`，没有代码、没有 `package.json`。规则靠评审维持，尚无 lint 强制。见 §7。

## 1. 顶层集合

每个目录只装**一类东西**，并为某个明确的理由赢得顶层位置。

| 目录 | 分类 | 为什么配得上顶层位置 |
|---|---|---|
| `core` | **应用运行时**〔桌面专用〕 | 与业务无关的基座。判据：把 `core` 抬到另一个 Electron 应用上，配别的业务代码，那就是另一个应用。装生命周期 / DI、路径、日志、窗口、调度、preboot、安全机制。**只服务 `src/main`**（§2.2）。 |
| `ipc` | **跨进程边界**〔桌面专用〕 | Electron 的核心机制，特殊到足以独立。主↔渲染唯一的受控通道，schema + 路由 + 错误映射。**只服务 `src/main`**。 |
| `data` | **数据层** | 通用业务数据存储，一等公民。仓储接口 + SQLite/PG 适配，屏蔽方言差异。 |
| `ai` | **核心域** | PointStudio 本身就是 AI 工作台，AI 是一等公民。装领域模型与用例、模型接入、工具协议、智能体。 |
| `features` | **领域模块（大）** | 大型业务领域，一个目录一个，自带 pages/components/hooks/services。**现在为空，这是刻意的**。 |
| `services` | **业务服务（小）** | 中小型业务服务，一件事一个文件或一个子目录。 |
| `utils` | **无状态辅助** | 跨领域、与业务无关的纯函数。它是唯一能被所有包（包括 `core`）依赖的东西，因此自己**零依赖**。 |
| `i18n` | **本地化** | 语言资源与 `t()` 解析。主进程与渲染进程共用同一套键——拆到两边会导致同一句话翻两次、漏一边。 |
| `policy` | **云端策略**〔云端专用〕 | 企业版的策略引擎：能力白名单、配额、审计规则、鉴权上下文。**个人版不用它**——本地单用户没有策略可言。 |
| `remote` | **远端协议**〔状态待决〕 | 原设计是「个人版 in-process、企业版 HTTP/WS，只换下层实现」。**个人版确定不连云后，它已无明确调用方**。要么删除，要么等企业版开工时重新定义，不要为它编造用途（§7）。 |
| `ui` | **跨端组件** | 跨端共享 UI（Tailwind + shadcn/ui）。它是唯一允许依赖 React 的包。 |

**命名遵循语义**：`core` / `data` / `ai` / `ipc` / `i18n` 是**单数**命名空间（每种只有一份）；`features` / `services` / `utils` 是**复数**分类桶（里面装多个）。

## 2. 依赖方向

组合根在 `src/main/index.ts`，它可以引用下面任何目录；其余目录之间**只能向下**。

```text
组合根（唯一可跨层引用）
  src/main/index.ts ──▶ 下列全部

内核分层（只许向下）
  features ──▶ services ──▶ ai ──▶ data ──▶ utils
                                   └─ i18n / ui 旁挂

桌面专用
  core ──▶ utils        Electron 运行时
  ipc  ──▶ core         主↔渲染边界

预留（当前无调用方，见 §7）
  policy ──▶ data       云端策略
  remote ──▶ utils      远端协议
```

规则：

1. **只能向下**，不能反向。`data` 不许 import `ai`，`ipc` 不许 import `features`。
2. **同一层内禁止横向依赖**：`feature` 之间不互相 import；`services` 之间可以调用但**不能成环**。
3. **`utils` 零依赖**：它是地基的地基，谁都能用它，它不能用别人。
4. **`core` 不认识业务**：出现 `Task` / `Session` / `Artifact` 就是放错了地方。
5. **`ui` 只进不出**：非 UI 目录不得 import `ui`；数据经 props 或上层注入，组件里不碰存储、网络、模型。

### 2.1 组合层的例外

`src/main/index.ts` 是唯一可以**跨层引用**的地方：它要把 `data` 的实现塞进 `ai` 的仓储接口、把 `ui` 挂到渲染进程、注册 `ipc` 路由。这是组合根（composition root）的本职，不算违规。

但方向是死的——**任何内核目录都不得 import `index.ts`**。它只做装配，不导出可复用逻辑；装配逻辑一旦需要被复用，就该下沉成 `services/` 下的一个模块。

### 2.2 两个壳与共享边界

PointStudio 有两个交付形态。它们**不是「同一构建的两个开关」，而是同一个内核的两个壳**：

| | 个人版 | 企业版 |
|---|---|---|
| 形态 | 开源桌面应用（Electron） | 云服务（SaaS，我们运营） |
| 部署 | 用户自己的电脑 | 我们的服务器 |
| 数据 | 全本地，永不外传 | 云端，多租户 |
| 模型 | BYOK（用户自带 Key） | 统一网关 + 配额 |
| 是否连云 | **不连** | 本身就是云 |

本仓库只装**个人版**。企业版（云服务）是独立的闭源代码树，不在这个仓库里——这是「个人版开源、企业版闭源」的物理落点。

因此 `src/main/` 下的目录分三类：

**内核**（桌面侧的全部业务能力）

- `ai` — 领域模型、模型接入、工具协议、智能体
- `data` — 仓储接口 + SQLite 实现
- `utils`、`i18n`、`ui`、`features`、`services`

**桌面专用**

- `core` — Electron 运行时
- `ipc` — 主↔渲染边界

**预留（当前无调用方）**

- `policy`、`remote` — 原本按云端设计。企业版独立建仓后，这两个目录应随之迁出或删除；**在那之前不要往里写代码**。

> 一条判断：**能跨端复用的必须是不依赖平台的纯逻辑。一旦某个目录 import 了 `electron`，它就不可能被服务端复用。**

### 2.3 禁止版本判断，也禁止预留多租户

- 任何位置出现 `if (isEnterprise)` 都属于违规。个人版没有版本分支。
- **不要**为了「将来支持企业」预留 `tenantId`、权限表、租户切换逻辑。企业版是独立代码树，从零写起，不需要个人版让路。**预留会污染当下的代码，而收益为零。**

## 3. 成长路径：从单文件到大领域

Cherry 的三级晋升，原样保留：

```text
services/<name>.ts         ← 默认形态：一个文件
   ↓ 一个文件装不下了
services/<name>/           ← 原地变成主题子目录
       index.ts            #   唯一的公共入口
       <Name>Service.ts    #   主实现
       helpers.ts          #   私有辅助
   ↓ 长成多文件的大领域
features/<name>/           ← 才升级成 feature
```

**规则**：

- **是晋升，不是默认**。不要为「预期中」的模块预先创建子目录或 feature。
- **不要跳级**。小业务一开始就建 feature，等于给三行代码修厂房。
- **目录名是主题名，不带 `Service` 后缀**；只有类文件保留后缀（`services/webSearch/WebSearchService.ts`）。
- **分类桶根没有 `index.ts`**：`services/` 和 `utils/` 是分类，不是模块。导入具体的文件或主题，不要导入整个桶。

## 4. 封闭顶层治理

> **顶层集合是封闭的——往 `src/main/` 下新增目录应当视为不在讨论范围内。**

新能力按性质归入既有分类，绝不给它一个新目录：

| 这个能力是…… | 归位 |
|---|---|
| 跑应用需要、与业务无关的 | `core` |
| 跨进程通信 | `ipc` |
| 数据存取、方言适配 | `data` |
| 与 AI 本质相关（模型、工具、智能体、领域模型） | `ai` |
| 一个业务功能，小 | `services` |
| 一个业务功能，大 | `features` |
| 纯函数、无状态 | `utils` |
| 用户可见文案 | `i18n` |
| 个人版 / 企业版的差异 | `policy`（仅企业版使用；个人版无策略层） |
| 与远端的协议、传输 | `remote`（**待决**，可能整体不需要，见 §7） |
| 人看的组件 | `ui` |
| 窗口、菜单、托盘、启动 | `src/main`（不进包） |

**能力要拆解，不要整体搬家**。一个横切能力（比如「通知」）不该新开目录，而应按性质拆开：规则进 `policy`、发送实现在 `services`、气泡组件在 `ui`、文案在 `i18n`。

## 5. 反模式

- 在 `core` 里写业务（`Task`、`Session`、`Artifact`）——它必须与业务无关。
- 在 `ai` 里直接 `app.getPath()` 或 `fetch` —— 平台与网络走注入。
- 业务代码直接 `getDb()` 或写 SQL —— 绕过 `data` 的仓储接口。
- 工具内部做权限判断 —— 权限归 `policy`（仅云端；个人版没有权限体系，工具只管执行）。
- 在 `ui` 里调用存储或模型 —— 组件应当只有 props 和事件。
- `feature` 之间互相 import，或外部深导入 `feature` / `services/<name>/` 的内部文件。
- 为单一能力新开顶层目录（§4）。
- 模块级可变状态藏在普通 camelCase 名下 —— 有状态就必须是类 + 单例 + `Service`/`Manager` 后缀。
- 硬编码用户可见文案 —— 走 `i18n`。

## 6. 当前状态（目标 vs 现状）

本文是目标，不是现状记录。**一旦某个缺口解决，就从表里移除**，不记「已完成」。

| 区域 | 现状 | 目标 |
|---|---|---|
| 全部目录 | `src/main/*` 只有 `README.md`，无代码、无 `package.json` | 按各包 README 落地 |
| `features/` `services/` `utils/` | 空目录 | 保持空，直到第一个够格的业务出现（§3） |
| 依赖强制 | 无 lint，方向靠评审维持 | 按 §2 配 `import/no-restricted-paths`（新增 devDependency 需先写 ADR） |
| `src/main` | 只有 `main/index.ts`、`preload/index.ts`、`renderer/` 骨架 | 按 Cherry `core/` 的结构组织：`bootstrap/` `window/` `ipc/` `paths.ts` `logger.ts` |
| `src/server` | 不存在 | 企业版即云服务，它是我们运营的服务端；等企业版开工时再建，不预创建 |
| `remote` | 空壳 | **待决**：个人版不连云，它已无明确调用方。要么删掉，要么等企业版开工时重新定义职责。不要为它编造用途 |
