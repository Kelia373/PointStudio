# 共享层（`src/shared`）

跨进程共享代码放在哪、什么时候才值得建，以及「只放类型和纯函数」的约束。

## 现状

**已建立**，唯一触发点正是 IPC 类型：`src/shared/types/ipc.ts` 放着 `chat:*` 的通道名、请求 / 结果类型与事件载荷。主进程、preload、渲染进程三方 import 同一份，避免字段名漂移。

## 什么时候建

当**主进程和渲染进程都要用同一份类型**时，才建 `src/shared/`。

典型的触发点只有两类：

1. **IPC 通道的请求 / 响应类型**——两边必须完全一致，各写一份必然漂移
2. **跨进程常量**——错误码、事件名、命令 ID

**不满足就不建。** 只被一边使用的类型放在那一边：主进程的放 `src/main/`，渲染进程的放 `src/renderer/`。

## 两条不变式

### 1. 必须两边都在用

判据很简单：这个文件被 `src/main` 和 `src/renderer` **同时** import 吗？

只被一个进程 import 的东西，不属于共享层。「以防万一先放这儿」是共享层最常见的腐烂方式——放的时候想着以后会用，结果一直没人用。

### 2. 只放类型和纯函数，不放状态

`src/shared` 里**不允许**出现：

- 模块级可变变量
- 单例（服务、管理器、注册表）
- 任何持有运行时状态的对象

理由：主进程和渲染进程是两个独立的 JS 运行时，`src/shared` 在**每个进程各加载一次**。所谓「共享单例」实际是两份互不相干的实例，改一份另一份不知道。

允许的：`type` / `interface` / `enum`、纯函数、常量、用 `new Map`/`Set` 从静态数据构建后冻结的查表。

有状态的类只从 `src/shared` 发出**定义**，实例由各进程自己 `new`。

## 目录

```
src/shared/
├── types/     跨进程类型
└── utils/     跨进程纯函数
```

两个桶都**不要**根 `index.ts`——桶是分类不是模块，导入具体文件（`@shared/types/ipc`），不要导入整个桶。

## 反模式

- 把只被主进程用的类型放进来「以后可能要用」
- `export const service = new SomeService()` —— 违反不变式 2
- 在共享层里读 `process.env` 或 `window` —— 那是各进程自己的事
- import `electron` 或 `react` —— 两边环境不同，一 import 就绑死了
- 因为没有地方放而扔进来 —— 那是「杂物间」的开始
