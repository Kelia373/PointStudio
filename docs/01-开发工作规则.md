# 01 · 开发工作规则

适用范围：本仓库所有人工与 AI 协作的改动。规则冲突时优先级：`AGENTS.md` > 本文件 > 局部约定。

## 1. 一个改动的生命周期

```
理解 → 勘查 → 方案 → 契约 → 实现 → 自检 → 评审 → 交付
```

| 阶段 | 产出 | 谁确认 |
| --- | --- | --- |
| 理解 | 一句话复述目标 + 验收标准 | 提任务的人 |
| 勘查 | 受影响文件/模块清单，现状结论 | 自查 |
| 方案 | 改什么、不改什么、风险、回滚 | **人确认后才写码** |
| 契约 | 失败的测试 / 明确的断言 | 人扫一眼 |
| 实现 | 小步提交，测试转绿 | — |
| 自检 | 见第 5 节清单 | 自查 |
| 评审 | 换一个上下文找茬 | 另一个 agent 或人 |
| 交付 | 变更说明 + 如何验证 | — |

## 2. 测试契约（硬规则）

- 新增接口/服务/数据表/迁移、修 bug、重构、涉及权限·金额·审计·并发·一致的代码 —— **必须先有失败测试**。
- 修 bug 的第一件事是写出能复现它的测试；没有复现测试的修复不予合并。
- 断言只描述行为，不描述实现细节（不比字段名、不用反射、不跳过钩子）。
- 允许不套用的场景：一次性脚本、探索原型、纯样式微调。**用了就要在 PR 说明为什么不需要。**

### 2.1 门禁在哪几层（已实现，不靠自觉）

| 层 | 触发 | 拦什么 | 文件 |
| --- | --- | --- | --- |
| 内容层 | `pre-commit` | 删改断言、`skip/xfail/@ts-ignore` 等豁免标记、`except: pass` | `scripts/hooks/pre-commit` |
| 提交信息层 | `commit-msg` | 新增测试文件却没写 `TDD-Red:` 说明 | `scripts/hooks/commit-msg` |
| 测试层 | `pre-push` + CI | 测试不通过 | `scripts/hooks/pre-push`、`.github/workflows/ci.yml` |

安装：`bash scripts/install-hooks.sh`（每个 clone 跑一次）。
钩子可以 `--no-verify` 绕，**CI 绕不过**——所以真正说了算的是 CI 那道。

**已知边界**：内容层看不见「新建测试文件时直接把实现的输出写成期望值」，因为新文件在 diff 里全是新增行。这条靠提交信息层的 `TDD-Red` 承担，本质是**留痕可追溯**，不是自动证明。要记得这一点，别以为它万无一失。

## 3. 分支与提交

- `main` 常绿；功能分支生命周期以「天」为单位，不做长跑分支。
- 提交：`type(scope): 摘要`（feat/fix/docs/refactor/test/chore/perf）。
- 一次提交只做一件事；重构与功能分开提交，方便回滚。
- 合并前 rebase 到最新 `main`，保持线性历史。

## 4. 依赖与选型

引入依赖是**架构决策**，不是顺手操作：

1. 先说清「现有能力为什么不够」；
2. 对比至少一个替代方案（含不引入的写法）；
3. 记录到 ADR；
4. 人确认后才加。

## 5. 交付前自检清单

- [ ] 计划和实际改动范围一致；超范围的部分已单独说明
- [ ] 新增行为有测试，且测试先红后绿
- [ ] 没有改断言来迁就实现（改过的话单独列出）
- [ ] 端到端跑过（涉及集成行为时）
- [ ] 没有密钥/令牌/真实数据进入 diff
- [ ] `ref/` 未被修改或提交
- [ ] 文档与规则已同步更新（行为变了，`docs/` 要跟着变）

## 6. 停止条件

出现任一情况，立刻停下来回到方案阶段：

- 同一个测试改三次还没绿；
- 实现开始「绕」：加特判、加兼容分支、加 try-catch 吞异常；
- 改动范围超出原计划；
- 需要修改「计划里说不能动」的契约；
- 你开始解释「为什么这样也能过」。

## 7. 文档规则

- 规范变更和代码变更同一提交内完成。
- 决策写进 `docs/adr/`，一个决策一个文件，**只有状态**：提议 / 已接受 / 已废弃。不写流水账。
- 文档写「现在成立的结论」；历史与过程放 ADR 或提交信息里。

## 8. 兼容契约（逐字节不许变）

来源：SkyWalking 的实践——每一个对外 DSL 语法、配置键、指标名和标签结构必须逐字节保持一致。

**范围**（只要命中就要有测试守着）：

- 对外 API：路径、方法、状态码、字段名与类型。
- 配置文件：键名、层级、默认值。
- 持久化格式：表结构、字段名、序列化格式。
- 工具/插件协议：能力描述、参数 schema、返回结构。

**规则**：

1. 改这些之前，先写一条对比测试锁住旧行为，再动实现。
2. 数据结构变更必须走迁移，不允许「兼容一下就好」的双分支暗中扩散。
3. 个人版与企业版共用内核，**行为对等就是契约**：同一输入两版产出必须一致，差异只允许出现在策略校验层。

## 9. 审查清单（审实现路径，不只审结果）

结果绿了不代表做法对。评审时逐条问：

- [ ] 有没有为了通过测试而加的特判、兼容分支、吞异常？
- [ ] 空值 / 空列表 / 超大值 / 并发两次，这里会怎样？
- [ ] 是否用了反射、字段名字符串比较、跳过钩子这类手段达成目的？
- [ ] 新依赖进来没有？进来是否走过 ADR？
- [ ] 触碰了第 8 节的兼容契约吗？有测试守着吗？
- [ ] 测试是在描述行为，还是在复述实现？
- [ ] 改动的文件是否与计划一致？超出的部分有没有单独说明？

做不到换人评审时，至少让作者用「找茬」的姿势重读一遍 diff，逐行问上面的问题。

## 8. 阶段出口（防止只写文档不产出）

一个阶段结束的标志不是「文档写完」，而是「有东西能跑」。

规范阶段的出口是三件事，全部完成才算过关：

1. 一条命令能把仓库跑起来（`git clone` 后无需口头指导）；
2. 一个测试能由红转绿（证明测试链路是通的）；
3. CI 能跑通（哪怕只有一个 job、只跑测试）。

此后的每个阶段，结束时必须有一个**新增的可运行物**：一个接口有响应、一条链路能端到端跑通、一个界面能操作。文档不计入产出。

`docs/` 下的编号文档上限 5 个。写满即停止新增，需要补充时改进现有文档，不新开编号文件。
