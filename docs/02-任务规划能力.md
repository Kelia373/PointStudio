# 02 · 任务规划能力

「任务规划」有两层含义，此处都覆盖：

- **A. 协作协议**：AI agent 接到一个开发任务后，怎么想、怎么拆、怎么执行、怎么收尾。
- **B. 产品能力**：PointStudio 自身必须具备的任务理解与规划内核（这是产品卖点）。

两层共用同一套骨架：**分级 → 澄清 → 勘查 → 计划 → 执行 → 校验 → 交付**。区别只是 A 面向研发过程，B 面向终端用户任务。

---

## A. 协作协议（研发过程）

### A1. 任务分级（先定级，再定流程）

| 级别 | 场景 | 流程 |
| --- | --- | --- |
| L0 | 问答、解释、查代码 | 直接答，不动文件 |
| L1 | 单点小改：改文案、修一个明确 bug | 一句话方案 → 直接做 → 说明验证方式 |
| L2 | 单模块功能：加一个接口/一个页面 | 书面计划 + 测试契约 → 做 → 自检 |
| L3 | 跨模块特性：涉及多层或数据结构变更 | 计划 + 影响面 + 迁移/回滚 → 人确认 → 分批提交 |
| L4 | 架构性变更：换存储、换协议、拆包 | 先写 ADR，人确认后拆成多个 L2/L3 执行 |

**定级错误是最大浪费**：把 L3 当 L1 做会毁结构，把 L1 当 L4 做会拖死节奏。

### A2. 计划必须回答的六件事

1. **目标**：做完之后，什么现象证明它成了（可验收）。
2. **不改什么**：明确划出禁区（对外的接口、数据结构、既有行为）。
3. **影响面**：哪些文件/模块/契约会被触碰。
4. **步骤**：拆成可独立验证的小步，每步能单独判断对错。
5. **风险与回滚**：最坏情况是什么，怎么退。
6. **验证方式**：跑什么、看什么、谁来确认。

缺任何一项，都不是计划，是愿望。

### A3. 澄清预算（VoI 判据）

不要靠「感觉不确定」决定问不问——模型的置信度校准很差。改用**信息价值**判断：

```
净收益(问) = 这个答案能改善多少决策 − 打扰人的成本
净收益 ≤ 0 → 不问，直接做并标注假设
```

落地规则：

- 最多问 **2 个**真正阻塞的问题；其余按假设推进，交付时标注。
- **一次只问一个维度**，问题要带比较或方向，让人好回答；不要开放式发问。
- 能靠读代码/读文档/跑命令消除的疑问，不许问人。
- 问的时候给选项和推荐项，答「你看着办」时按推荐项执行并写明假设。

**反面模式（有名字的失败）**：Act-without-Asking——在含糊指令下自己猜着往下做。实证研究显示这个失败模式下，「反复检索继续硬推」的成功率甚至低于「直接猜」，而「先查再问」最高。**不确定性出现时，正确动作是外部交互，不是加倍努力。**

### A4. 执行循环

```
小步实现 → 跑测试 → 绿则提交 → 回看计划是否仍成立 → 下一步
```

- 每步一次提交；提交信息能独立读懂。
- 计划中途失效（发现前提错误）→ **停止执行，重新出计划**，不硬推。
- 长任务用 todo 列表显式维护进度，避免「做到哪了」这种失忆。

### A5. 收尾

交付时必须包含：做了什么、为什么这么做、怎么验证、还有什么没做。
「没做的部分」比「做了的部分」更需要写清楚。

## B. 产品能力：规划内核

### B1. 输入

- 用户任务描述（自然语言，可能含糊）
- 工作区上下文（文件、会话历史、既有产物）
- 能力清单（可用工具与其能力边界、成本、耗时、副作用）
- 策略约束（个人版：宽松；企业版：权限、数据分级、可审计、成本上限）

### B2. 输出：计划对象（Plan）

```jsonc
{
  "goal": "可验收的目标陈述",
  "assumptions": ["把不确定的地方写成假设"],
  "steps": [
    { "id": 1, "action": "干什么", "tool": "用哪个能力",
      "input": {}, "expect": "怎么判断成功", "risk": "low|mid|high" }
  ],
  "stopConditions": ["什么情况下必须停下来问人"],
  "rollback": "失败了怎么退",
  "costEstimate": { "tokens": 0, "wallClockSec": 0 }
}
```

要点：**每步必须有可判断的 `expect`**。没有验收方式的步骤不允许进入计划——否则执行阶段无法判断对错，只能靠感觉。

### B3. 规划原则

1. **先探后拆**：信息不足时，第一步永远是「获取信息」，而不是猜着做。
2. **最小可行步**：一步只做一件能独立验证的事；步骤粒度 = 可回滚粒度。
3. **副作用前置声明**：写文件、发网络请求、花钱、改配置，必须在计划里显式标出，执行前获得许可。
4. **失败可重规划**：某步失败 → 判断是「参数错」「前提错」还是「能力不足」，分别对应重试 / 重规划 / 上报。同一路径重试上限 3 次。
5. **不做隐性扩张**：计划外的顺手改动一律不做，记下来另开任务。

### B4. 澄清与自主的平衡

- 目标含糊但**风险低**：自行假设并标注，直接做。
- 目标含糊且**有副作用**（花钱、改数据、对外发送）：必须先确认。
- 判断标准是**不可逆性**，不是「重不重要」。

### B5. 个人版 / 企业版差异（规划层）

| 关注点 | 个人版 | 企业版 |
| --- | --- | --- |
| 澄清策略 | 偏自主，假设即做 | 涉及数据外发/资费必须先确认 |
| 能力范围 | 全部本地能力 | 受策略白名单约束，越权步骤直接拒绝 |
| 成本 | 用户自己承担 | 计划需带成本估算，可设上限熔断 |
| 审计 | 过程日志本地留存 | 每步记录：谁批准、用了什么、产出什么 |
| 失败处理 | 重试与降级 | 重试与降级 + 事件上报 |

**共同点**：计划对象结构一致、执行循环一致、停止条件一致。差异只体现在**策略校验层**，不进内核分支——这是避免两版分裂的关键约束。

### B6. 可观测性（规划能力怎么才算「有」）

- 计划可回放：给定输入，能复现出计划。
- 每步有明确状态：待执行 / 执行中 / 成功 / 失败 / 已跳过。
- 失败能定位到「哪一步、因为什么」。
- 用户能中途改主意（暂停、改目标、砍步骤），且不丢失已完成部分。

## 待定

- 计划是纯 LLM 生成，还是「模板 + LLM 填充」（影响稳定性与成本）。
- 重规划是否保留历史计划版本供对比。
- 多 agent 并行时计划如何切分与合并（当前只按单 agent 串行设计）。

## 参考资料（2026-11 调研）

**为什么 agent 会不问就干**

- [MID-Bench / Act-without-Asking](https://aclanthology.org/2026.emnlp-main.1236.pdf) — 即使提供「呼叫用户」动作，开放权重 GUI agent 平均仅 0.1% 的情况会用；提出澄清门（clarification gate）作为免训练改进。
- [DiscoBench](https://arxiv.org/pdf/2606.27669) — 含糊检测与有效提问是两种独立能力；`SearchHeavyGuess` 低于 `DirectGuess`，`SearchThenAsk` 最高。

**该怎么决定问不问**

- [Value of Information 框架](https://arxiv.org/html/2601.06407v1) — 净收益 = 信息价值 − 打扰成本；不靠可调阈值。
- [REVOIR / CLEAT](https://arxiv.org/pdf/2610.12655) — 用配对 rollout 估计「残余查询价值」，并让提问策略随结果自适应。

**怎么在工程上强制先规划**

- [Plan-then-Execute](https://arxiv.org/pdf/2509.08646) — 人类介入的最佳位置是「计划生成后、任何动作前」（Plan-Validate-Execute）；P-t-E 同时提供控制流完整性。
- [LangChain: Plan-and-Execute Agents](https://langchain.com/blog/planning-agents) — planner / executor 分离，显式「想清楚全部步骤」能提升完成率。
- [Claude Code Plan Mode](https://code.claude.com/docs/en/permission-modes) — plan 模式下物理禁止改文件，批准后才执行；计划文件可审阅、可持续对照。
- [AI-native SDLC: plan mode as default](https://academy.claude.com/courses/ai-native-sdlc-playbook/plan-mode) — 计划成为 `plan.md` 进入审计链，实现偏离计划要同提交更新。
- [Kiro Specs](https://kiro.dev/docs/specs) / [Fowler: Spec-Driven Development](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html) — requirements → design → tasks 三阶段逐段批准，规格成为主产物。
