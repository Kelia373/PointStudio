# ADR 0007：壳、注册表与插件整合框架

- 状态：已定稿（设计），实现待开工
- 影响范围：`src/renderer`（主要）、`src/main`（P2 起）、构建配置
- 相关：[plugin-development.md](../references/plugin-development.md)（作者视角）、[ui-remediation.md](../references/ui-remediation.md)（施工单）

## 背景

要让第三方能"按需给客户端加功能页、改界面"，现在的渲染层撑不住：

- `App.tsx` 6 行，直接渲染 `ChatPanel`，没有壳、没有路由 → 新页面无处挂
- `ChatPanel.tsx` 823 行，会话/消息/流式/计划状态全在组件内 → 插件读不到共享状态
- 组件全靠 `import` 硬引用（9 处）→ 无法替换"改任何东西"
- `app.css` 1793 行单体 → 插件无法只带自己的样式
- renderer 构建未外部化 React → 插件组件一挂就两份 React

同时，侧栏已有一个类插件位（`FEATURES` 数组 + 固定/更多 + 「待接」标记），
说明产品形态上已经默认"会有扩展"，只是数据写死在组件里。

## 决策

### 一、三张注册表 + 一个壳

| 层 | 职责 | 谁写 |
| --- | --- | --- |
| **路由注册表** `routes/registry.ts` | 有哪些页面（id/title/icon/order/component） | 内置页 + 插件 |
| **导航注册表** `nav/registry.ts` | 页面如何在导航里出现（侧栏功能位、底栏两端、顶栏右侧） | 内置 + 插件 |
| **组件注册表** `registry/components.ts` | 可被替换/插入的 UI 单元 | 内置组件注册为 `builtin.*`，插件可覆盖 |
| **壳** `shell/Shell.tsx` | 导航 + 内容区 + 全局横幅 + 浮层宿主 | 只有宿主 |

**关键决定：内置组件也必须走组件注册表。** 不这么做，"改任何东西"是空话——
页面里 `import MessageBubble` 的地方就是插件的墙。

### 二、插槽（slots）清单

插槽是"插入型"扩展点，与"替换型"的组件覆盖分开。首版定 10 个，名字即契约：

| 插槽 | 位置 | props | 期 |
| --- | --- | --- | --- |
| `sidebar.features` | 侧栏第二段（现 `FEATURES` 位置） | `{ navigate }` | P0 |
| `appbar.left` / `appbar.right` | 全宽底栏两端（现为占位） | `{}` | P0 |
| `topbar.right` | 顶栏检查器键左侧 | `{ conversation }` | P0 |
| `conversation.composer.dock` | 输入框上方 | `{ draft, busy }` | P0 |
| `sidebar.bottom` | 侧栏第四段之后 | `{}` | P1 |
| `conversation.banner` | 消息流上方横幅区 | `{ conversation }` | P1 |
| `conversation.message.actions` | 每条消息操作行 | `{ message }` | P1 |
| `shell.overlay` | 整页浮层（与 drawer 同级） | `{ close }` | P1 |
| `sidebar.agents.actions` | Agent 段标题右侧 | `{ agents }` | P2 |

组件覆盖键：`chat.bubble`、`chat.composer`、`chat.empty`、`sidebar.item`、`settings.section`。

### 三、状态外置：单一 store + 选择器

```
store/chatStore.ts   conversations, activeId, messages, busy, inflightId,
                     mode, planRun, warn/error/info, contentWidth
store/settingsStore.ts  provider 视图
```

- 实现用 React 自带 `useSyncExternalStore`，**不引入 Redux/Zustand**（硬约束：不新增运行时依赖）
- 组件只能通过 `useStore(selector)` 订阅切片；写入只能调 store 的 action
- 现有纯函数（`chatState`、`planRunState`、`filterConversations`）**原样复用**，矩阵测试不变

理由：插件页面要读"当前会话/消息"，状态必须在组件之外；组件覆盖后，状态也不能跟着组件被卸载。

### 四、插件运行时

```
plugins/loader.ts    读 manifest → 校验 apiVersion → 执行入口 → 收集 disposer
plugins/context.ts   组装 RendererContext / HostContext
```

- **双入口**：`main`（主进程 `apply(ctx)`）、`renderer`（渲染进程 `apply(ctx)`），至少一个
- **React 外部化**：renderer 构建 `rollupOptions.external: ['react','react-dom']`，宿主提供单实例
- **生命周期**：`apply` 返回的每个注册都返回 disposer，卸载时逆序执行
- **安装即信任**：不做沙箱、不做能力拦截（与 Alpha 决策一致）；只保留三条硬边界

### 五、三条硬边界（不可商量）

1. 不许替换根节点（页面必须渲染在壳分配的内容区）
2. 不许自带第二份 React（外部化，否则 hooks 崩）
3. 不许读别的插件的 DOM / 样式 / 内部状态

### 六、兜底（不是权限模型）

- 每页一个 `PageBoundary`：插件页抛错 → 该页降级为错误卡片，壳与其它页不受影响
- 插件状态机：`enabled / disabled / quarantined / incompatible / degraded`
- 阈值：连续 3 次异常 / 5 分钟 → 自动 quarantine；启动 >5s → 跳过本轮；上次非正常退出 → 下次插件全禁启动并提示
- 设置里每个插件一行：版本、health、**禁用 / 回滚上一版 / 卸载**

## 被否掉的方案（以及为什么）

| 方案 | 否决理由 |
| --- | --- |
| 直接上 iframe / 独立 WebContents 沙箱 | 观感与交互一致性差；当前阶段自由度优先；隔离可以后加，壳和注册表**不能后加** |
| 引入 Redux / Zustand | 违反「不新增运行时依赖」；`useSyncExternalStore` 足够 |
| 插件整包替换 App | 一旦换根，用户连"禁用插件"的入口都点不到 |
| 先做市场后做样板 | 空货架；顺序应是 3 个官方插件 → 打磨 API → 开放 |
| 把插槽做成万能容器（任意位置可插） | 无法保证布局与主题继承，且每次改版都会破坏插件 |

## 迁移路线

| 期 | 内容 | 验收判据 |
| --- | --- | --- |
| **P0** | 路由注册表 → 壳 → 状态外置 → 内置组件入注册表 → 导航注册表（`FEATURES` 改造）→ React external → 样式拆分 | `ChatPanel` ≤400 行；`grep "import MessageBubble"` 归零；353 测试全绿；`tsc`/build 通过；真窗口功能逐条走通 |
| **P1** | 插件加载器（本地目录）+ `RendererContext` + `PageBoundary` + 插件列表（启停） | 手写 `hello` 插件出现在导航并能渲染；故意抛错只坏自己那页 |
| **P2** | `components.override` + 主题包 + Host 入口（工具/命令/IPC 前缀） | 用插件替换 `chat.bubble`；插件注册的工具能被 Agent 调用 |

施工细目见 [ui-remediation.md](../references/ui-remediation.md)。

## 风险

1. **props 即契约**：组件被覆盖后，改 props 会打破外部插件。缓解：新增字段只能可选，删改必须升 `apiVersion` 并留一版兼容层。
2. **覆盖粒度过大**：允许覆盖 `chat.bubble` 是红利也是债，每次重构都要顾及第三方。缓解：首版只开放 5 个键，其余保持内部。
3. **无沙箱**：安装即信任意味着恶意插件能做任何事。缓解：只从本地目录安装（不做远程一键装）、插件列表显式列出安装来源；企业版另加白名单（不在本 ADR 范围）。
4. **并发改造**：分支上有另一方的 UI 提交，P0 动 `ChatPanel`/`Sidebar` 前需确认对方停手。

## 未决

2. 主题包是否允许携带作用域 CSS（会让"换皮"变强，也让冲突变复杂）
3. 企业版白名单与审计的具体形态
