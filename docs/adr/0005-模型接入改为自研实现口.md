# ADR 0005 · 模型接入改为自研实现口，DeepSeek 首发

- 状态：**已接受**
- 日期：2026-11-23
- 决策人：Alpha
- 取代：`ADR 0002` 决策表第 8 条（原定 Vercel AI SDK 6，Provider 差异不自己写）

## 背景

`ADR 0002` 第 8 条当时的判断是「自写多 provider 适配是纯负债，AI SDK 已覆盖」。Alpha 现在改为反方向：**我们自己提供实现口（port），先实现 DeepSeek，后续再补其他平台**。

理由（决策人给出，本文只记录，不复述论证过程以外的内容）：

- 接入层是产品的核心差异点之一，不想被第三方抽象决定能做什么、不能做什么；
- 首发只需要一个平台，接口面很小，没有「多 provider 适配」的历史包袱；
- 不引入运行时依赖，`ADS 0004` 的零依赖骨架得以保持。

## 决策

| # | 决策 | 选择 |
| --- | --- | --- |
| 1 | 依赖 | **不引入** `ai` / `@ai-sdk/*`；用 `fetch` + SSE 自写 |
| 2 | 抽象 | 自定义 `ChatProvider` 实现口，位于 `src/main/ai/providers/` |
| 3 | 首发实现 | `deepseek.ts`（OpenAI 兼容协议：`POST /chat/completions`，`stream: true`） |
| 4 | 扩展方式 | 新平台 = 新增一个实现文件实现同一接口，不改上层；**不做**「一个万能 OpenAI 兼容适配器吃掉所有平台」的假统一 |
| 5 | 密钥 | 由外壳注入，provider 只接受「拿 Key 的函数」，禁止自己读环境变量 / 配置文件 |
| 6 | 错误 | 归一为 `ProviderError`（含 `code` 与 HTTP status），原始报文只进日志，不透给界面 |

## 实现口契约

```ts
interface ChatStreamRequest {
  apiKey: string
  baseUrl: string
  model: string
  messages: Array<{ role: 'system' | 'user' | 'assistant'; content: string }>
  params?: Partial<ModelParams>
  signal?: AbortSignal
}

interface ChatProvider {
  readonly id: string                       // 'deepseek'
  streamChat(request: ChatStreamRequest): AsyncIterable<string>
}
```

`streamChat` 产出**增量文本片段**，不产出半成品消息对象；拼接与落库归调用方。

## 后果

**正面**：零运行时依赖；接口面由我们定义；支持中断（`AbortSignal`）；单平台实现可以写得很实（超时、错误码、SSE 边界）。

**负面 / 风险**：

- 每个新平台都要自己写一遍协议细节（鉴权头、端点、参数名差异），这是被放弃的 AI SDK 价值；
- SSE 解析要自己处理：跨 chunk 的多字节字符、`data:` 多行、`[DONE]`、以及「半行」缓冲；
- 平台方改协议时由我们承担跟进成本。

## 待定

- 是否需要一个「OpenAI 兼容」实现给第三方兼容端点（Ollama、vLLM、其他中转）复用 —— 先不做，等第二个平台真的出现再判断是否收敛。
