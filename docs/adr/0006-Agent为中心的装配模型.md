# ADR 0006：以 Agent 为中心的装配模型（身份 / 项目 / 派遣）

- 状态：已接受（2026-11-24，Alpha 拍板）
- 影响范围：`data`（会话字段）、`services`（会话与执行）、后续的 `agent` 模块
- 取代：ADR 0002 中「会话绑定助手」的隐含模型（不删除旧字段，改变语义）

## 背景

现在的模型是「会话绑一个助手」：`conversations.assistantId`。它把三件事糊在了一起——谁在做、在哪个项目做、这次执行了什么。助手改了提示词或换了工具之后，历史会话就对不上「当时到底是谁、带着什么能力在干」。

产品定位也随之明确：**这套软件不是工作流编排器，是「培养 agent」**。以几个长期存在的 agent 为核心，技能与工具按需装配到 agent 上，工作区是它们被派去做事的地方。任务卡偏给人用。

## 决策

### 1. 三层，各管各的

| 层 | 是什么 | 归属 |
| --- | --- | --- |
| **Agent** | 身份：技能、工具、记忆 | 长期，跨项目存在 |
| **Workspace** | 项目：文件、约定、上下文 | 与 agent 互不认识 |
| **任务卡 Task** | 把「做什么」挂到「谁做 + 在哪做」 | 人使用；派遣 / 挂载语义 |

任务卡不是 agent 的成员关系，也不要求声明「需要什么技能」——**由人决定派谁**，系统只提示能力缺口。

### 2. 会话 = 一次派遣的执行记录

会话记录执行时的快照，而不是一个软引用：

```
Task（做什么） → Run（一次派遣：agent 快照 + workspace + 模型参数） → Session（上下文窗口）
```

- 一张任务卡可以有多个 Run（重试、换人、分阶段）；一个 Run 可以跨多个上下文窗口。
- 会话保留 `(taskId?, agentId, agent 当时的技能/工具清单版本, workspaceId)` 快照。没有 taskId 的会话是**临时会话**（自由聊天），聊出价值后可以「提拔」成任务卡。
- 记忆提炼挂在 **Run 结束**，不是会话结束——否则长任务聊到一半就被"提炼"，记的是半截结论。

实现上先做最小改动：`conversation` 增加**可选** `taskId` / `model` / `params`（缺省继承全局），消息 schema 不动。任务卡作为独立模块另起一轮（要建卡、状态机、挂载关系与迁移，不是加字段能解决的）。

### 3. 模型是执行参数，走会话级

全局设置只存**凭据 + 默认值**；会话存**覆盖值**（model 与采样参数一起，否则无法复现）。界面上的模型切换放输入栏，因为它表达的是「这次执行用什么」。

### 4. 记忆全部归 agent，靠作用域区分

采纳「记忆只在 agent 私域」——一个 agent 的成长跟着它走，可携带、可分发。但不能无作用域，否则 A 项目学到的命令会带进 B 项目还很自信。

```
MemoryItem { agentId, scope: 'global' | 'project:<id>', kind: 'preference' | 'fact' | 'skill-note',
             source: runId, text, createdAt, locked? }
```

- 派工时按 `global + 当前项目` 过滤。
- **事实进项目作用域，偏好进 global**——同一件事两边都存必然互相冲突。
- 项目档案是由 agent 记忆按 `project:<id>` 聚合出的**只读派生视图**，不提供独立写入通道，避免双写。
- 记忆必须可看、可改、可删、可锁（`locked` 表示用户钉住，提炼不许覆盖）。没有这个，"培养"就是黑箱。

### 5. 成长信号：先做行为信号，不做通用评分

「用户拿 agent 干什么」无法预先定义，因此**不做统一考题**。分三层，先只做第一层：

- **L1 行为信号（默认开）**：重发率、中途停止、输出被改写、同卡重试次数、工具失败率、耗时。全部来自现有事件流，不需要懂业务。
- **L2 自我回放（留接口不实现）**：只在自己成功跑过的 Run 上重跑，比"改装备前后有没有退步"，不做绝对打分。这正是 Run 作为事实被保留下来的第二个理由。
- **L3 用户自定义考题**：给愿意投入的人，从最近的成功 Run 一键生成本地考题集。

界面形态是**成长时间线 + 记忆浏览器**，不是分数榜。

## 后果

- 首页导航以 **agent** 为中心（人是主角），会话退化为「这个人的工作记录」，项目是二级导航。这会重排现有以会话为中心的布局。
- 新增 `clipboard:write-text` 等跨进程能力时，遵循既有的通道一致性守卫。
- 需要补的字段一律**可选**，且缺省分支必须有测试（消息 schema 的既有演进规则同样适用）。

## 未决

1. 项目档案作为派生视图是否足够（新 agent 进项目看到的是别人代理出的经验）。
2. 多 agent 协作（handoff）在 Run 里如何表达。
3. 技能与工具的版本化与分发格式（与插件市场对齐）。
